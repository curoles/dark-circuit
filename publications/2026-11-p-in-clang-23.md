# Turning on P in clang 23: what the compiler does with RISC-V's packed SIMD

*November 2026. Igor Lesik. Code: [dark-circuit](../README.md), an open library of hardware
blocks and the small RISC-V cores built from them.*

RISC-V's packed SIMD extension, P, is a draft, and clang 23 already has it, as an
experimental extension. I used clang 23.1.6 to build the tests of Mig3, my 5-stage RISC-V
core, which runs 63 of P's instructions, and an int8 neural-network kernel that runs 3.6
times faster with them. Along the way I wrote down what the compiler does once P is
turned on. Some of it I expected; some of it trapped my core.

The short version: there are intrinsics for the simple lane operations but none for
multiplies, the loop vectorizer does not use P, and yet clang uses P all over ordinary C
code, mostly for 64-bit arithmetic on register pairs.

## 1. Turning it on

P is not on by default, and two things are required. Both errors say exactly what they
want:

```
$ clang-23 ... -march=rv32im_p0p21
invalid arch name 'rv32im_p0p21',
requires '-menable-experimental-extensions'
for experimental extension 'p'

$ clang-23 ... -menable-experimental-extensions \
    -march=rv32im_p
experimental extension requires explicit
version number `p`
```

- **The version is part of the flag.** `-march=rv32im_p0p21` means P version 0.21; the
  next clang may have 0.22, and then the old flag stops working. My build asks clang
  instead: `clang -print-supported-extensions` lists `p 0.21`, and CMake builds the flag
  from that line.
- **P is one extension.** clang 23 offers no subsets of it: `-march` with P promises the
  whole draft, several hundred instructions. That matters later.
- **gcc 12.2 has no P.** It stops with "cannot find default versions of the ISA extension
  `p'". I did not try newer gcc releases.

## 2. Three version numbers for one draft

- **The specification** is version 0.6, in review.
- **clang** calls its P version 0.21.
- **riscv-opcodes**, the machine-readable encoding tables, says 0.20 in its P table.

Three numbers, but the encodings agree. Mig3's decoder is generated from riscv-opcodes, and
its decode test is assembled by clang; I also assembled every instruction clang emitted in
the examples below and compared the bits against riscv-opcodes' patterns. All of them
match. For a draft that still changes, that agreement is what I check whenever either side
moves.

## 3. Intrinsics: lanes yes, multiplies no

clang ships `riscv_packed_simd.h`, 644 lines. It defines lane types (`int8x4_t`,
`int16x2_t`, and 64-bit ones on register pairs) and intrinsics for:

- **add and subtract,** wrapping and saturating, and the averaging forms;
- **minimum and maximum,** absolute value and absolute difference, sums of absolute
  differences;
- **lane compares** producing masks, and a merge by mask;
- **logic, negate, shifts** by a scalar amount, and sums across the lanes.

What is missing is every multiply: the lane multiplies, and the dot products, PM4ADDA.B
and friends, which are exactly what an int8 kernel wants. P's intrinsics document already
names them, so my kernel defines the one it needs with inline assembly, under the
documented name:

```c
static inline int32_t
__riscv_pm4adda_i8x4(int32_t rd,
                     int8x4_t a, int8x4_t b) {
    __asm__("pm4adda.b %0, %1, %2"
            : "+r"(rd)
            : "r"((uint32_t)a),
              "r"((uint32_t)b));
    return rd;
}
```

When a clang arrives that has the real one, this definition collides with it and the
build fails, which is the reminder to delete it.

## 4. What clang does with P on its own

The surprise is not the intrinsics but ordinary C. I compiled small functions at -O2, with
and without P, and compared the instructions:

- **Constants.** `return 0x00010001;` is LUI and ADDI without P, and one PLI.H with it, a
  packed load-immediate that repeats a 10-bit value in both halves. `0x05050505` becomes
  PLI.B. Any constant that happens to repeat per lane qualifies, packed data or not.
- **64-bit arithmetic on RV32.** P has instructions on register pairs, and clang uses them
  for `int64_t`: a widening multiply `(int64_t)a * b` is one WMUL instead of MUL and MULH;
  a 64-bit add is ADDD instead of three ADDs and an SLTU; SUBD likewise; shifts across the
  pair become NSRLI and WSLAI.
- **Multiply-add.** `acc + a * b` on 16-bit values becomes MACC.H00, and so do the dot
  product loops over `int16_t` and `int8_t` arrays, one element per step.
- **Clamps.** Clamping to [-128, 127] is one SATI. A saturating 16-bit add written in C
  becomes P's 32-bit saturating SADD on values shifted to the top half, then shifted back.

And what it does not do: vectorize. A loop adding two arrays of `int8_t`, `int16_t` or
`int32_t` stays one element per step with P on; nothing packs four bytes into a register.
The dot product loop is not packed either; it gets MACC.H00, one product per step.

The 64-bit cases matter most, because they are everywhere. TensorFlow Lite's rounding
doubling high multiply, the core of int8 requantization, is a few lines of `int64_t`:

```c
int64_t ab    = (int64_t)a * b;
int32_t nudge = ab >= 0 ? (1 << 30)
                        : (1 - (1 << 30));
return (int32_t)((ab + nudge) /
                 ((int64_t)1 << 31));
```

With P, its body has WMUL, two ADDDs, NSRLI and WSLAI, register-pair instructions all,
and no packed data in sight.

## 5. CoreMark with P

I compiled all five CoreMark sources with P, at -O2 and -O3. The only P instruction clang
uses is MACC.H00: once in each of the three matrix multiply functions, three times in
`matrix_test`, and twice in `main`. Nothing from the lane instructions, no register pairs.
So CoreMark with P on measures one 16-bit multiply-add, not packed SIMD.

## 6. A core with part of P

Mig3 decodes 63 instructions of P: the one-cycle lane operations, the packed load-immediate
and the multiplies the int8 kernel needs. It has no register pairs. The first time the
kernel ran, it trapped on an illegal instruction: the requantization, plain C with 64-bit
arithmetic, had become WMUL and ADDD.

The flag promises the whole extension, so the fix is to say it only where it is true:

- **P only in the files that need it.** The kernel's P loop is the one file compiled with
  P; the driver, the reference version and the requantization are compiled without. CMake
  takes two architectures per test: one for the P sources, one for the rest.
- **A test that lists the instructions.** A small script disassembles the P objects and
  compares every mnemonic with the instructions Mig3's decoder names. A new clang that
  finds another use for P fails this test, not the core at run time.

With that, the kernel runs: an int8 fully connected layer, plain C against PM4ADDA.B, every
output compared, about 9,220 cycles against 2,560.

## 7. What I take from it

- **`-march` is a promise, not a hint.** The compiler uses whatever the flag allows,
  wherever it helps, including in code that has nothing to do with packed data.
- **For P, "wherever it helps" means 64-bit arithmetic first.** On RV32 that is the
  biggest effect of turning P on: register-pair instructions in every `int64_t` function.
- **Intrinsics for the loops that matter, for now.** Without vectorization and without
  multiply intrinsics, packed code is written by hand, with inline assembly for the
  missing parts, named so the next clang retires it.
- **Check the binary against the core.** With a draft extension and a partial core, a list
  of the instructions actually used is cheap and catches the mismatch at build time.

## How I measured, and where the code is

Ubuntu clang 23.1.6, target `riscv32-unknown-elf`, `-O2`, with and without
`-menable-experimental-extensions -march=rv32im_zba_zbb_p0p21`; instructions read from the
assembly output and from `llvm-objdump-23 -d -M no-aliases`; CoreMark from eembc's
repository. The P flag is found in `cmake/riscv.cmake` (`dc_riscv_p_march`); the
instruction check is `tools/check_insns.py`, run as the test `design_mig3_int8_insns`; the
kernel is `test/design/mig3/int8_kernel*.c`. Mig3's P subset and why it stopped where it
did are in `rtl/design/mig3/p_profile.md` and `kb/rtl/design/mig3/p_profile.yaml`.
